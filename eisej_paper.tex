\section{Introduction}\label{sec:Introduction}

Software quality is a fundamental aspect of software engineering because it directly influences maintainability, evolvability, and long-term maintenance costs. As software systems continue to grow in size and complexity, maintaining high-quality source code becomes increasingly important to ensure efficient software evolution and reduce technical debt. One of the most widely recognized indicators of poor design quality is code smell, which refers to structural characteristics in source code that suggest potential design deficiencies without necessarily affecting the software's functional correctness \cite{Fowler1999}\cite{Palomba2018}. Although code smells do not immediately introduce defects, their accumulation can increase code complexity, reduce readability, complicate testing activities, and ultimately increase maintenance effort.

Various approaches have been proposed to detect code smells, ranging from rule-based and metric-based techniques to more recent machine learning-based methods \cite{Pereira_dos_Reis_2021}\cite{THAKUR2026112784}. Compared with manually defined detection rules, machine learning approaches are capable of learning complex relationships among software metrics and automatically identifying patterns associated with different types of code smells \cite{THAKUR2026112784}\cite{Alodibat2026}\cite{MESBAH2026108242}. Consequently, machine learning has become an increasingly popular solution for improving the scalability and adaptability of code smell detection across different software projects.

Recent studies have shown that machine learning has become one of the dominant approaches for code smell detection due to its ability to learn complex relationships among software metrics. Our previous review of code smell detection research over the last decade also indicates a clear shift from traditional rule-based techniques toward machine learning and optimization-based approaches \cite{WibowoICITEE2025}, highlighting the increasing importance of high-quality datasets for model development and evaluation. Optimization techniques such as Particle Swarm Optimization combined with Random Forest have demonstrated promising improvements in detection performance, suggesting that advances in learning algorithms should be accompanied by equally reliable datasets to achieve robust and reproducible results \cite{Madeyski2017}\cite{Wibowo2026}\cite{Bishop2026}\cite{Destefanis2026}.

The effectiveness of machine learning models, however, depends heavily on the quality of the datasets used for training and evaluation \cite{MESBAH2026108242}. A reliable dataset should contain accurate code smell labels \cite{zhang2026sacscodesmelldataset}, comprehensive software metrics \cite{ZHANG2024112131}, and a reproducible metric extraction process to ensure consistent results across different studies \cite{LEWOWSKI2022106783}. In addition, thorough validation of the extracted metrics and dataset characteristics is essential to establish confidence in the resulting models \cite{Alomari2025}. Without these properties, machine learning experiments may produce unreliable results and become difficult to reproduce or compare with previous studies.

Despite the growing adoption of Kotlin as the preferred programming language for modern Android application development, publicly available datasets specifically designed for Kotlin-based code smell detection remain scarce. Existing code smell datasets are predominantly constructed from Java open-source projects, with systematic literature reviews identifying Java as the primary language represented in publicly available datasets \cite{Zakeri_Nasrabadi_2023}\cite{app14146149}\cite{Alomari2025}\cite{11316404}\cite{madeyski_2020_3666840}. Consequently these datasets do not adequately capture the language-specific syntax and structural characteristics of Kotlin applications, limiting their applicability for Kotlin-oriented software quality research. Furthermore, currently available Kotlin datasets generally lack comprehensive classical software metrics, validated Abstract Syntax Tree (AST)-based metric extraction pipelines, and detailed documentation to support reproducibility. Some existing studies also rely on regular-expression-based techniques or parsers with limited support for Kotlin syntax, potentially reducing the accuracy and consistency of the extracted metrics. Consequently, the absence of a validated and reproducible Kotlin software metrics dataset limits the development, evaluation, and fair comparison of machine learning-based code smell detection methods. Although sophisticated learning algorithms have been proposed, their performance remains highly dependent on the quality of the underlying datasets. Existing studies have primarily focused on improving code smell classification performance through feature engineering, model optimization, and learning algorithms \cite{Zakeri_Nasrabadi_2023}\cite{ZHANG2024112131}, whereas comparatively less attention has been devoted to dataset construction, dataset validation, and reproducible metric extraction processes \cite{ZHANG2024127014}. Recent surveys have identified dataset quality, annotation reliability, and validation mechanisms as important yet underexplored challenges that directly affect the reliability and reproducibility of machine learning-based code smell detection \cite{zhang2026sacscodesmelldataset}.

This study constructs a primary software metrics dataset for Kotlin applications using an AST-based metric extraction pipeline implemented with Kopyt. Kopyt is an open-source parser implemented in pure Python that parses Kotlin source code into an Abstract Syntax Tree (AST) \cite{pypi_kopyt}. The parser represents Kotlin language constructs as hierarchical AST nodes, enabling systematic traversal of classes, functions, declarations, statements, and expressions for static code analysis and software metric extraction \cite{kotlin_spec}. Unlike text-based parsing approaches, AST traversal preserves the syntactic structure of Kotlin programs, allowing software metrics to be computed directly from language constructs rather than textual patterns \cite{chen2023acerastbasedgraphgenerator}. The results obtained from previous study are that the Detekt program can detect various Kotlin-based programming codes well but still has a percentage difference of 48.75\% with manual calculations for some advanced metric categories \cite{WibowoICITDA2025}. The proposed pipeline extracts a comprehensive set of classical software metrics, constructs method-level datasets, assigns Long Method and Feature Envy labels according to the adopted labeling procedure, and validates the resulting metric values and dataset quality. After cleaning malformed records, the reconciled Long Method and Feature Envy datasets contain the same 71,259 method-level instances and 89 attributes, including 82 software metrics. The remainder of this paper is organized as follows. Section 2 reviews related work on software metrics, code smell detection, and existing datasets. Section 3 describes the dataset construction methodology, including repository selection, source-code collection, metric extraction, data cleaning, and code smell labeling. Section 4 presents metric verification and dataset quality and statistical analyses. Section 5 discusses the findings and threats to validity, while Section 6 concludes the paper.

This paper makes four main contributions. First, it constructs a Kotlin software metrics dataset containing 82 software metrics and code smell labels for Long Method and Feature Envy detection. Second, it proposes a reproducible AST-based software metric extraction pipeline using Kopyt to extract method-level and class-level metrics from Kotlin source code. Third, it provides multi-level metric verification through manual source-code inspection, independent AST-based verification using Detekt, and algorithm-level verification of coupling metrics. Fourth, it provides a systematic dataset-quality and statistical assessment, including malformed-record detection, missing-value analysis, duplicate analysis, class-distribution analysis, and correlation analysis, thereby supporting reproducible future research on Kotlin code smell detection.

\section{Background and Related Work}\label{sec:Background}
\subsection{Code Smell Detection and Software Metrics}

Initially code smell detection was mostly performed using rule-based and metric-based approaches. As software complexity increased, these approaches faced limitations in handling varying project characteristics, leading to the development of machine learning-based methods \cite{THAKUR2026112784}\cite{Alodibat2026}\cite{MESBAH2026108242}. Recent studies have shown that machine learning and deep learning models can achieve high code smell detection performance by exploiting combinations of software metrics as predictive features \cite{Dewangan2022}. Effective feature representation enables these models to capture complex relationships among software quality attributes that are difficult to express using manually defined detection rules \cite{Liu2021}\cite{abdelkader2025novel}.

\subsection{Evolution of Machine Learning-Based Code Smell Detection}

Over the past decade, research on code smell detection has shifted from rule-based approaches to machine learning and optimization-based approaches \cite{THAKUR2026112784}\cite{Alodibat2026}\cite{MESBAH2026108242}. A previous review study (A Decade of Code Smells Detection: Evolution, Challenges, and Optimization Strategies) \cite{WibowoICITEE2025} showed that improving detection performance increasingly focused on feature selection, hyperparameter optimization, and the use of more sophisticated learning models. However, the study also identified that dataset quality and availability remain key challenges, limiting the reproducibility and comparability of results between studies.

These findings have served as the basis for further research focused on improving detection methods. One such study is the Enhanced Code Smell Detection Using Random Forest Optimized with Particle Swarm Variants study \cite{Wibowo2026}, which integrates feature selection and hyperparameter optimization using various Particle Swarm Optimization (PSO) variants to improve Random Forest performance. The results showed that the combination of feature selection and hyperparameter optimization significantly improved detection accuracy. This study used the Fontana dataset \cite{Fontana2017}\cite{Mhawish2020}\cite{Zellagui2026}, developed for Java projects, and therefore did not adequately represent the characteristics of the Kotlin language.

\subsubsection{Kotlin-Based Code Smell Detection}
The increasing adoption of Kotlin as the primary language for Android application development has spurred research specifically addressing code smells in Kotlin projects \cite{Dewangan2023}\cite{ugli2025codesmells}. One previous study, "Custom Rule-Based Feature Engineering for Code Smell Detection in Kotlin Using Detekt," \cite{WibowoICITDA2025} developed a rule-based feature extraction process using Detekt to obtain software characteristics related to code smells. This study demonstrated that Detekt can be used as a starting point for developing features for code smell detection in Kotlin.

This study focused on the feature engineering process and did not yet produce a validated software metrics dataset or a reproducible metrics extraction pipeline. Furthermore, the features obtained relied on Detekt rules and therefore did not directly capture the extraction of classic software metrics through program syntax structure analysis. These findings indicate that research on code smell detection in Kotlin is still in the development stage of detection methods, while the development of standard datasets usable by the research community is still relatively limited. Despite the growing interest in machine learning-based code smell detection, the availability of standardized, high-quality benchmark datasets that can be reliably shared and reused by the research community remains limited. Recent studies have emphasized the need for reproducible datasets, consistent annotation procedures, and publicly accessible benchmarks to enable fair comparison and reproducible evaluation of detection approaches. \cite{PROKIC2024103168}\cite{SLIVKA2023102999}\cite{zhang2026sacscodesmelldataset}\cite{Alomari2025}.

\subsection{Existing Code Smell Datasets}
Most datasets used in code smell detection research are developed using Java projects, such as PROMISE \cite{Gupta2025}, Qualitas Corpus \cite{Tempero2010}\cite{Terra2013}, and the Fontana Dataset \cite{Fontana2017}. These datasets have become primary references in the development of various classification methods because they provide software metrics and code smell labels. Most of these datasets were not designed for Kotlin and therefore lack the ability to adequately represent the syntax and structure of the language. Consequently, the availability of validated datasets specifically designed for Kotlin applications remains limited, creating a gap for research on language-specific software metric extraction and machine learning-based code smell detection.

In addition to the limitations of the programming language \cite{Santana2024} and numerous software engineering datasets have been proposed, previous studies have reported that dataset construction procedures are often insufficiently documented, particularly regarding data extraction, preprocessing, and validation. Such limitations hinder reproducibility and make it difficult for other researchers to assess the correctness and reliability of the resulting datasets \cite{Gonzalez-Barahona2012}\cite{Gonzalez-Barahona2023}\cite{lefeuvre2023fingerprintingbuildinglargereproducible}. As a result, research reproducibility is limited and the development of new methods requiring high-quality datasets is difficult \cite{Bosu_2013}\cite{Gupta2025}\cite{Alomari2025}. Limited availability of validated benchmark datasets restricts the reproducibility of empirical software engineering studies and makes it difficult to develop, evaluate, and compare new machine learning-based code smell detection methods in a reliable and consistent manner.

\subsection{Research Gap}
Based on the review in the previous subchapter, it can be concluded that code smell detection research has progressed through three stages. The first stage focused on the development of rule-based detection methods and software metrics. The next stage focused on utilizing machine learning and model optimization to improve classification performance. More recent research has begun exploring code smell detection in Kotlin, but still focuses on developing detection methods and feature engineering.

However there is no public dataset available for Kotlin that simultaneously provides comprehensive classical software metrics, a validated and reproducible Abstract Syntax Tree (AST)-based extraction pipeline, comprehensive dataset quality analysis, and initial benchmarks using machine learning. As shown in Table \ref{tab:dataset_comparison} this gap is the primary motivation for this research: to build a primary dataset of software metrics for Kotlin and an AST-based extraction pipeline using Kopyt so that it can serve as a reference in future machine learning-based code smell detection research.

\section{Dataset Construction Methodology}\label{sec:Method}
This chapter explains the methodology used to build a primary dataset of software metrics for code smell detection in Kotlin applications. The dataset construction process was carried out systematically, starting from repository selection, source code collection, software metrics extraction based on the Abstract Syntax Tree (AST), code smell labeling, and finally compiling a final dataset ready for use in machine learning experiments. All stages in Figure \ref{fig:pic_studymethodology} were designed to be reproducible using the same pipeline, resulting in a consistent dataset that can be reused by other researchers.

\subsection{Repository Selection}

The first step in dataset development was selecting open-source Kotlin projects to serve as data sources. GitHub was selected for this repository, as it offers a diverse range of projects with varying characteristics and open documentation and development history. To ensure the quality and representativeness of the dataset, each repository was selected based on a series of inclusion and exclusion criteria, such as Kotlin language dominance, active project status, and source code completeness. This selection process aims to obtain a collection of projects that reflect real-world software development practices, ensuring that the extracted software metrics can represent the characteristics of Kotlin applications in general.

\subsection{Data Collection}

Once a repository is selected, all source code is collected and processed through the dataset development pipeline. The process begins with cloning the repository, followed by parsing Kotlin files using the Kopyt library to create an Abstract Syntax Tree (AST). The AST structure is then used as the basis for extracting software metrics for each analyzed method and its enclosing class. The extracted records are subsequently subjected to data-quality checks and code smell labeling before being compiled into the final datasets. The pipeline is designed to preserve the same method-level observations across the Long Method and Feature Envy labeling tasks, enabling direct comparison of the two code smell labels after data cleaning.

\subsection{Metric Extraction}

Software metrics extraction is a key step in this research because it determines the quality of the resulting dataset. Unlike approaches that rely on regular expressions or text pattern matching, this research uses an Abstract Syntax Tree (AST)-based approach through the Kopyt library to obtain a structural representation of Kotlin source code. All software metrics are calculated through an AST traversal process, thus recognizing various Kotlin syntax constructs more accurately and reducing errors due to code variations. This pipeline is used to calculate various classic software metrics, including complexity, size, cohesion, and coupling metrics. In addition to explaining the definition of each metric, this subsection also outlines the implementation mechanism of the extraction algorithm used so that the calculation process can be reproduced in future research.

\subsubsection{AST Generation Using Kopyt}
The first step in the software metrics extraction process is to build a structural representation of the source code using an Abstract Syntax Tree (AST). This research utilizes Kopyt, a Python-based Kotlin parser capable of generating ASTs in accordance with Kotlin grammar. Each source file is parsed into a tree structure that represents syntactic elements, such as class declarations, functions, properties, expressions, and control structures. AST representation allows the analysis process to be based on program structure, rather than simply matching text patterns, resulting in more accurate and consistent information. Furthermore, using Kopyt allows the extraction pipeline to be run automatically without relying on the Android development environment or the project's compilation process.

\subsubsection{Software Metrics Extraction}

Once the AST is successfully created, the next step is to extract software metrics from each analyzed code entity. The extraction pipeline is designed to calculate various classic software metrics commonly used in code smell detection research, including size metrics, complexity metrics, coupling, cohesion, inheritance, and response metrics. All metrics are calculated through an AST traversal of relevant nodes, enabling comprehensive recognition of Kotlin's syntax characteristics. This approach avoids various limitations of regular expression-based methods, such as misidentification due to variations in writing format or the use of more complex Kotlin syntax features.

\subsubsection{Implementation of Metric Extraction Algorithms}

Each software metric is implemented as an extraction module that operates independently on the AST structure. The extraction algorithm utilizes a traversal process through specific nodes according to the definition of each metric. For example, the size metric is calculated based on the number of relevant declarations and lines of code, while the complexity metric is obtained by identifying branching and looping structures in the AST. The coupling metric is analyzed by tracing relationships between classes through object declarations, inheritance, interface implementations, and method calls. This modular approach allows each algorithm to be validated separately and simplifies the addition of new software metrics without changing the entire extraction pipeline.

\subsubsection{Pipeline Reproducibility}

One of the main goals of this research is to produce a software metrics extraction pipeline that can be reproduced by other researchers. The entire process, from source code parsing and AST generation to software metrics extraction and dataset construction, is implemented in a deterministic pipeline. By using the same configuration, parser, and extraction algorithm, the pipeline will produce consistent software metrics values ​​for identical source code. Furthermore, comprehensive documentation regarding the extraction stages, metric definitions, and dataset structure is provided so that other researchers can replicate the dataset construction process or develop the pipeline for different metrics or code smells.

\subsection{Code Smell Labeling}

After metric extraction and data-quality processing, each retained method instance is assigned code smell labels for Long Method and Feature Envy. The labeling procedure must be reported explicitly because the validity of the resulting classification targets depends on the source and reproducibility of the labels. In the present dataset, the final common dataset contains 71,259 method instances, with 232 Long Method instances and 250 Feature Envy instances.

The exact label-generation mechanism should be described here using the actual procedure employed in the study. In particular, the final manuscript should state whether the labels were obtained through expert annotation, predefined detection rules, previously trained machine learning models, or a combination of these procedures. Only one verified description should be used consistently throughout the Abstract, Methodology, Results, Discussion, and Conclusions.

\subsection{Dataset Schema}

The final datasets are organized at the method-instance level. Each row represents one retained Kotlin method and contains 89 attributes: 82 software metrics, six metadata attributes (\texttt{instance\_id}, extraction date, project, package, class, and method), and one code smell label. The Long Method dataset uses \texttt{is\_long\_method} as its target attribute, whereas the Feature Envy dataset uses \texttt{is\_feature\_envy}. After data cleaning, both datasets contain the same 71,259 method instances, which enables direct analysis of the relationship between the two code smell labels.

\section{Results}\label{sec:Results}

\subsection{Metric Verification}

The proposed AST-based extraction pipeline aims to accurately extract software metrics representing the structural characteristics of Kotlin source code. Before the constructed dataset can be considered suitable for machine learning-based code smell detection, the correctness of the extracted metrics must be systematically verified. Since the dataset contains both method-level and class-level metrics with different computational characteristics, this study employs three complementary verification approaches. Simple metrics that can be directly observed from source code are verified through manual inspection, structurally complex metrics are verified using an independent AST-based implementation, and metrics requiring sophisticated inter-class dependency analysis are validated through algorithm-level verification on representative methods. This multi-level verification strategy provides comprehensive evidence regarding the correctness and reliability of the proposed extraction pipeline.

\subsubsection{Verification Strategy}

Three complementary verification strategies were employed according to the computational characteristics of each software metric.

First, metrics whose values can be directly derived from Kotlin source code were verified through manual source code inspection. These metrics mainly represent software size, complexity, and basic method characteristics, allowing their values to be independently recalculated according to their formal definitions.

Second, metrics describing cohesion, class design, and structural relationships were verified using an independent AST-based implementation provided by the Detekt static analysis framework. Since Detekt constructs and traverses Kotlin Abstract Syntax Trees independently from the proposed Kopyt-based pipeline, comparing the outputs generated by both implementations provides strong evidence regarding the correctness of the extracted metrics.

Finally, several metrics requiring sophisticated inter-class dependency analysis could not be directly validated using the available Detekt implementation because they involve semantic relationships beyond the metrics currently supported by the framework. Therefore, these metrics were validated through algorithm verification using representative methods. For each selected method, the intermediate computation steps defined by the proposed extraction algorithm were manually traced and compared with the values generated by the implemented pipeline.

\subsubsection{Selection of Representative Metrics}

Although the proposed dataset contains a comprehensive collection of software metrics, verifying every extracted metric individually would be impractical. Therefore, this study adopts a representative metric verification strategy based on the feature selection results obtained from our previous studies on Long Method and Feature Envy detection \cite{Wibowo2026}.

Previous studies identified twelve representative software metrics for Long Method detection and another twelve representative metrics for Feature Envy detection. These metrics consistently demonstrated the highest contribution to machine learning classification performance and therefore represent the most informative software characteristics for the two code smell types.

Despite targeting different code smells, several representative metrics are shared by both detection models because they describe fundamental structural properties of software. Specifically, LOC, CYCLO, MAXNESTING, TCC, and AMWNAMM were identified as dominant predictors for both Long Method and Feature Envy. Since these metrics have identical formal definitions regardless of the target code smell, verifying them separately would introduce unnecessary duplication without providing additional evidence regarding the correctness of the extraction pipeline.

After removing duplicated metrics, the verification process focuses on nineteen unique representative metrics covering software size, complexity, cohesion, coupling, method interaction, method characteristics, and class design. Verifying this representative metric set provides confidence that the proposed AST-based extraction pipeline accurately extracts the software characteristics required for multiple machine learning-based code smell detection tasks.

\subsubsection{Algorithm Verification}

Unlike software metrics such as LOC, Cyclomatic Complexity, or Maximum Nesting Level that can be verified directly through manual inspection, several coupling-based metrics require more sophisticated analysis because their values depend on relationships among classes, method invocations, and attribute accesses throughout the program. Consequently, verifying these metrics requires confirming not only the extracted values but also the correctness of the underlying extraction algorithms.

This study therefore performs an algorithm verification for four representative coupling metrics, namely Access to Foreign Data (ATFD), Foreign Data Providers (FDP), Changing Methods (CM), and Changing Fields of Non-Accessor Methods (CFNAMM). These metrics were selected because they represent the core characteristics of Feature Envy detection and involve the most complex analysis within the proposed AST-based extraction pipeline. The verification was conducted by manually tracing Kotlin source code, identifying all relevant method invocations and foreign attribute accesses according to the formal metric definitions, and comparing the manually derived values with those produced by the proposed Kopyt-based extraction algorithm.

Two representative methods from the Inure project were selected to illustrate the verification procedure, namely BaseActivity.onCreate() and SplashScreen.proceed(). These methods were intentionally chosen because they exhibit multiple interactions with external classes while representing different levels of coupling complexity. During manual verification, every foreign attribute access, accessed external class, internal method invocation, and non-accessor method interaction was identified directly from the source code before calculating the corresponding metric values.

The \texttt{onCreate()} method in the Android Activity lifecycle should ideally only initialize the main visual components and perform basic binding. However, based on the AST extraction, the \texttt{onCreate()} method in this base class was detected as a Long Method with a significant number of lines of code (LOC). Most software metrics exhibit right-skewed distributions where the median is considerably smaller than the mean. \subsubsection{Distribution Analysis}

Histogram analysis in Figure \ref{fig:LOC_histogram_lm}\ref{fig:CYCLO_histogram_lm}\ref{fig:LOC_histogram_fe}\ref{fig:CYCLO_histogram_fe} further confirms the skewed nature of software metric distributions. The distribution analysis is performed for both the Long Method and Feature Envy datasets to verify that both datasets exhibit consistent statistical characteristics.

The distribution of code-smell labels shows a highly imbalanced class structure in both datasets. Among the 71,259 valid method-level instances, 232 instances (0.33\%) are labeled as Long Method (LM), while 71,027 instances (99.67\%) are labeled as non-Long Method. Similarly, 250 instances (0.35\%) are labeled as Feature Envy (FE), whereas 71,009 instances (99.65\%) are labeled as non-Feature Envy. Thus, positive instances account for less than 1\% of the observations for both code smells. This distribution reflects the relatively sparse occurrence of the two code smells at the method level in the analyzed dataset, but it also introduces a substantial class-imbalance issue for subsequent statistical analysis and machine-learning experiments. In particular, evaluation procedures based only on overall accuracy may provide an overly optimistic assessment because a classifier can obtain high accuracy by predominantly predicting the majority class. Therefore, class-sensitive evaluation measures and appropriate validation strategies should be considered when the dataset is used for code-smell detection or predictive modeling.

\section{Discussion}\label{sec:Discussion}

\subsection{Reliability of the Proposed AST-Based Extraction Pipeline}

The verification results demonstrate that the proposed Kopyt-based extraction pipeline is capable of accurately extracting representative software metrics from Kotlin source code. Rather than relying on a single verification approach, this study combines manual source code inspection, independent AST-based verification using the Detekt framework, and algorithm-level verification for metrics requiring inter-class dependency analysis. The three complementary strategies validate different aspects of the extraction process, thereby providing stronger evidence of correctness than a single verification technique alone.

Manual verification confirms that software metrics directly observable from the source code, including software size, logical complexity, nesting structure, local variable usage, parameter count, and method interaction, are computed exactly according to their formal definitions. Meanwhile, metrics involving class cohesion, coupling, inheritance, and design characteristics exhibit consistently high agreement with values produced by the independent AST implementation. The additional algorithm-level verification further confirms that complex metrics such as ATFD, FDP, CM, and CFNAMM correctly implement their mathematical definitions for representative Kotlin methods. Collectively, these results indicate that the proposed extraction pipeline reliably captures both method-level and class-level software characteristics required for constructing machine learning datasets.

Unlike previous dataset construction approaches that typically rely on a single parser or manual validation of a limited number of metrics, the proposed verification framework evaluates representative metrics covering multiple software quality dimensions. Consequently, the reliability of the constructed dataset is supported not only by high agreement values but also by the complementary nature of the adopted verification strategies.

\subsection{Quality of the Constructed Dataset}

The quality assessment demonstrates that the final datasets satisfy several important characteristics required for empirical software engineering research. The raw Long Method export contained 71,623 records, including 364 malformed records that produced 31,304 apparent missing values because of malformed CSV quoting. Structural inspection of the Feature Envy export identified two additional malformed records. After these records were excluded, the Long Method and Feature Envy datasets were reconciled to the same 71,259 method-level instances, with no missing values or duplicate complete records remaining.

The final dataset contains 89 attributes, including 82 software metrics and seven non-metric attributes consisting of six metadata fields and one code smell label. This distinction is important because the number of dataset attributes should not be interpreted as the number of extracted software metrics.

Descriptive analysis indicates that the extracted software metrics exhibit diverse and right-skewed distributions reflecting the variability of Kotlin source code. Although several representative metrics contain extreme values, these observations correspond to genuinely large or structurally complex methods rather than automatically indicating extraction errors. Such observations should therefore be interpreted in the context of the metric definitions and the underlying source code.

The class distribution is highly imbalanced for both code smells. Long Method represents 0.33\% of the final common dataset, while Feature Envy represents 0.35\%. This imbalance should be considered when the dataset is used for supervised learning because accuracy alone may be dominated by the majority class. Evaluation measures such as precision, recall, F1-score, and precision--recall analysis are therefore more informative for future classification experiments.

\subsection{Characteristics of Representative Software Metrics}

Statistical analysis demonstrates that the representative software metrics capture complementary aspects of Kotlin software quality. Metrics such as LOC, Cyclomatic Complexity, and Maximum Nesting Level primarily describe method size and logical complexity, whereas cohesion metrics including TCC and LAA characterize structural relationships among class members. Coupling metrics such as ATFD, FDP, and FANOUT measure interactions with external classes, while class-level metrics including WOC and AMWNAMM describe higher-level design characteristics.

The correlation analysis further indicates that although several complexity-related metrics exhibit moderate positive correlations, many representative metrics remain relatively independent from one another. This observation suggests that the selected metrics describe different structural properties rather than redundant information. Consequently, the feature selection process performed in previous studies successfully identified software metrics that collectively provide comprehensive information for code smell detection.

The existence of only five overlapping metrics between the representative feature sets of Long Method and Feature Envy further supports this observation. Although both code smells share several general software characteristics, each code smell is primarily characterized by distinct software quality dimensions. Long Method emphasizes software size and logical complexity, whereas Feature Envy relies more heavily on coupling and inter-class interaction metrics. This finding explains why different subsets of representative metrics are required to achieve accurate detection performance for different code smell types.

\subsection{Implications for Machine Learning-Based Code Smell Detection}

The verified dataset provides a reproducible foundation for future machine learning-based code smell detection research. The final common dataset contains the same 71,259 method-level instances for both Long Method and Feature Envy, while maintaining separate target labels. This structure enables researchers to compare models for the two smell types without introducing differences in the underlying set of analyzed methods.

The severe class imbalance should be explicitly considered in future experiments. Because positive instances represent less than 1\% of the final dataset for both smell types, a classifier may achieve high overall accuracy while providing poor detection of positive instances. Consequently, future studies should report class-sensitive evaluation measures and should clearly distinguish between data-level balancing, algorithm-level cost sensitivity, and threshold adjustment.

The dataset also supports a range of machine learning techniques beyond any single classifier used in the labeling procedure, if applicable. The extracted metrics can be utilized by ensemble learning algorithms, gradient boosting models, automated machine learning frameworks, and feature selection techniques. However, future models should be evaluated independently from the procedure used to generate the code smell labels in order to avoid circular evaluation.

Another important implication is the reproducibility of the proposed extraction pipeline. Because the extraction process is implemented directly on Kotlin Abstract Syntax Trees, future researchers can reproduce the dataset construction process, extend the implemented software metrics, or apply the pipeline to additional Kotlin repositories without changing the underlying extraction methodology.

\subsection{Comparison with Previous Dataset Construction Approaches}

Previous software metric datasets have predominantly focused on Java systems and frequently relied on existing metric extraction tools, parser-based approaches, or manually constructed benchmark datasets. Although these datasets have significantly contributed to software engineering research, many of them do not fully support Kotlin-specific language constructs introduced in modern Android development.

In contrast, the proposed dataset is specifically designed for Kotlin applications and employs a dedicated AST-based extraction pipeline implemented using Kopyt. This implementation enables direct traversal of Kotlin syntax trees while preserving language-specific constructs that may not be accurately handled by language-independent parsers. Moreover, the proposed pipeline simultaneously extracts method-level and class-level software metrics within a unified framework, facilitating the construction of comprehensive datasets for multiple code smell detection tasks.

The additional verification performed using an independent AST implementation further distinguishes this work from previous dataset construction studies. Rather than validating only the resulting datasets, this study explicitly verifies the correctness of the extraction algorithms, thereby increasing confidence in both the extracted software metrics and the constructed dataset.

\subsection{Threats to Validity}

Several limitations should be considered when interpreting the results of this study. Regarding internal validity, although multiple verification strategies were employed, implementation errors may still exist for software metrics that were not included among the representative verification set. In addition, the data-quality analysis identified malformed CSV records in the exported datasets. These records were removed before the final reconciliation, but their presence indicates that the data-export process itself is a potential source of error and should be controlled in future releases.

Regarding construct validity, the implemented software metrics follow the formal definitions adopted in this study. Manual verification, independent AST-based verification, and algorithm-level validation collectively reduce the possibility that the extracted metrics deviate from their intended definitions. However, the independent verification results were not uniformly identical: one evaluated metric achieved only 68\% agreement with Detekt. This discrepancy indicates that some metric definitions or implementation details may require further investigation.

The validity of the code smell labels is another important consideration. The manuscript must explicitly document the actual label-generation mechanism and its provenance. Expert annotation, predefined detection rules, and previously trained machine learning models represent different forms of ground truth and have different implications for reproducibility and validity. Therefore, the final manuscript should use one consistent description of the labeling procedure and report the information required to reproduce it.

With respect to external validity, the constructed dataset consists exclusively of Kotlin open-source projects. Consequently, the reported findings may not be directly generalizable to other programming languages such as Java, Scala, or Swift. Moreover, the Feature Envy positives are concentrated in a limited number of projects: 250 positive instances occur in 12 projects, with 179 instances (71.6\% of all Feature Envy positives) originating from a single project. This concentration may introduce project-specific characteristics into the positive class.

Finally, conclusion validity may be affected by the severe class imbalance of both smell labels. Only 232 of the 71,259 final instances are labeled Long Method, while 250 are labeled Feature Envy. Future machine learning studies should therefore use class-sensitive evaluation procedures and, where appropriate, repository-level validation to reduce the risk that project-specific characteristics dominate the reported performance.

\section{Conclusions}\label{sec:Conclusions}

This study presented an AST-based software metric extraction pipeline for constructing a validated dataset to support Kotlin code smell detection. The proposed approach utilizes the Kopyt framework to traverse Kotlin Abstract Syntax Trees and extract software metrics at the method and class levels. The resulting dataset contains 89 attributes, including 82 software metrics, six metadata attributes, and a code smell label.

Data-quality reconciliation identified malformed records in the raw exports. The initial Long Method export contained 71,623 records, including 364 malformed records associated with 31,304 apparent missing values. The Feature Envy export contained 71,261 records, of which two were identified as malformed during structural inspection. After cleaning and reconciliation, both code smell datasets contain the same 71,259 method-level instances with no missing values or duplicate complete records.

The final common dataset contains 232 Long Method instances (0.33\%) and 250 Feature Envy instances (0.35\%). Thirteen method instances are labeled with both code smells, while 219 are Long Method only and 237 are Feature Envy only. These results demonstrate that the two code smell targets can be analyzed on a common set of Kotlin method instances while preserving their distinct labeling characteristics.

To ensure the reliability of the extracted metrics, three complementary verification strategies were employed. Manual source-code inspection was used to validate directly observable software metrics, an independent AST-based implementation using the Detekt framework verified structurally complex metrics, and algorithm-level verification examined coupling-related metric implementations. Most evaluated metrics showed high agreement, although one metric exhibited substantially lower agreement and should be investigated further.

Overall, the proposed pipeline and cleaned dataset provide a reproducible foundation for empirical studies of Kotlin software quality and code smell detection. Future work should expand the repository population, independently validate the code smell labels, investigate the remaining metric discrepancies, and evaluate machine learning models using class-sensitive and repository-aware validation procedures.
